# 压测数据对照说明

## 一、理论值 vs 实际值

| 指标 | 理论值 | 你看到的 JMeter 值 | 说明 |
|------|--------|-------------------|------|
| 串行 (10 任务) | 10 × 100ms = **1000ms** | Avg **2021ms** | 约 2 倍，见下文 |
| 并行 (10 任务) | ~**100ms** | Avg **2739ms** | ForkJoinPool 竞争导致（已修复） |

## 二、数据对不上的常见原因

### 1. 测量口径不同

| 来源 | 测量内容 | 典型值 |
|------|----------|--------|
| **JMeter** | 端到端：网络 + Tomcat 排队 + 业务 + 序列化 | 总是更高 |
| **/benchmark 接口** | 仅业务逻辑（不含网络、序列化） | 更接近理论值 |

两者本身就不会完全一致，JMeter 通常比 /benchmark 高 50–200ms（视网络和负载而定）。

### 2. 任务数量不一致

- 未传 `count` 时：默认 **10** 个任务
- 若 JMeter 请求 `/serial?count=20`：串行 ≈ 20 × 100ms = **2000ms**

你看到的串行 Avg 2021ms，与 count=20 非常接近，建议检查 JMeter 是否带了 `?count=20` 或类似参数。

### 3. 并行曾使用 ForkJoinPool（已修复）

之前并行用 `ForkJoinPool.commonPool()`，并发压测时多请求共享少量线程，导致：

- 并行 Min 323ms：低负载时能跑快
- 并行 Avg/P99 变差：高负载时线程池饱和，排队严重

已改为专用 50 线程池，重新压测后并行应明显优于串行。

## 三、如何验证数据是否合理

### 方法 1：用 /benchmark 做基准

```bash
# 10 个任务（默认）
curl "http://localhost:8080/benchmark"

# 20 个任务
curl "http://localhost:8080/benchmark?count=20"
```

预期（仅业务耗时）：

- count=10：serialMs ≈ 1000，parallelMs ≈ 100–150
- count=20：serialMs ≈ 2000，parallelMs ≈ 100–200

### 方法 2：JMeter 配置建议

| 配置项 | 建议 | 说明 |
|--------|------|------|
| 线程数 | 1（先验证） | 排除并发对线程池的影响 |
| 请求路径 | `/serial` 和 `/parallel` 都不带 `?count=` | 使用默认 10 个任务 |
| 循环次数 | 5–10 | 便于观察稳定性 |

单线程、无 count 时，预期：

- 串行：~1000–1200ms（含网络等）
- 并行：~150–300ms（含网络等）

### 方法 3：对照公式

```
串行耗时 ≈ count × 100ms + 固定开销
并行耗时 ≈ 100–200ms + 固定开销（与 count 关系不大）
```

若串行 ≈ 2000ms，则 count 很可能为 20。

## 四、快速自检清单

- [ ] JMeter 请求 URL 是否包含 `?count=`？若有，确认 count 值
- [ ] 是否已使用修复后的代码（专用线程池）重新压测？
- [ ] 是否先用单线程压测验证，再逐步提高并发？
- [ ] 是否用 `/benchmark` 对比过纯业务耗时与 JMeter 端到端耗时？
